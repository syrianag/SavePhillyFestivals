# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository shape

Nx monorepo with two independently releasable projects:

| Nx project | Location | What it is |
|---|---|---|
| `save-philly-festivals` | `apps/save-philly-festivals` | Next.js 16 App Router app (JS, not TS) — Auth.js v5 credentials auth, Prisma 7 + PostgreSQL |
| `n8n` | `apps/n8n` | Dockerized N8N automation runtime with its own PostgreSQL, driven by `tools/scripts/n8n-ops.mjs` |

They use **separate databases** and never share a release. `nx.json` sets `defaultProject: save-philly-festivals`, so bare `nx run <target>` resolves there.

**There is only one npm package in this repo.** `pnpm-workspace.yaml` declares `packages: ['apps/*']`, but neither app directory has a `package.json` — the single package is the **root** one, and it is *named* `save-philly-festivals`. Consequences worth internalizing before you type a command:

- `pnpm --filter save-philly-festivals <cmd>` does **not** select the app; it resolves to the repo root, so any config path relative to the app dir (`--config vitest.config.js`) fails.
- `pnpm exec` from inside `apps/save-philly-festivals` fails outright with `ERR_PNPM_RECURSIVE_EXEC_NO_PACKAGE`.
- Every Nx target sets `cwd: {projectRoot}`, which is what actually makes tool configs resolve. Prefer `nx run`; when you must bypass Nx, `cd` into the app dir and call the binary from the root `node_modules/.bin` directly.

`apps/save-philly-festivals/CLAUDE.md` imports `AGENTS.md`, which is auto-generated by `next dev` and warns that this Next.js version differs from training data — consult `node_modules/next/dist/docs/` (resolved from the app dir, not the repo root) before writing framework code.

## Commands

Always run pnpm from the workspace root; npm workflows are unsupported.

```sh
pnpm run dev            # runs `check` first via predev, then next dev
pnpm run dev:web        # same dev server, skips the predev gate
pnpm run check          # lint + typecheck across all projects
pnpm run build          # nx run-many -t build --all
pnpm run test           # all projects: web vitest + n8n workflow contract tests
pnpm run test:coverage
pnpm run e2e            # Playwright, full 5-browser matrix
pnpm run verify         # the full gate: prisma validate + audit + coverage + n8n test/validate + lint + build
```

Root scripts are grouped `db:*`, `deploy:*`, `n8n:*`, `ops:*`, with `:web`/`:n8n` variants for single-project runs. `deploy`/`deploy:web` dispatches the gated GitHub production workflow and refuses unless both `RELEASE_SHA` and `BACKUP_REFERENCE` are set.

Nx scans every non-ignored directory, so local git worktrees under `.worktrees/` register duplicate projects and fail the entire project graph. `.gitignore`, `.nxignore`, and `.vercelignore` all exclude them; the `.nxignore` entry is what protects remote builds, where the other two may not apply.

Single unit test / single case — `--args` passes straight through to vitest:

```sh
pnpm exec nx run save-philly-festivals:test --args="tests/unit/social-feed-service.test.js"
pnpm exec nx run save-philly-festivals:test --args="tests/unit/social-feed-service.test.js -t 'rejects unmoderated posts'"
# bypassing Nx requires both the app cwd and the root-installed binary:
cd apps/save-philly-festivals && ../../node_modules/.bin/vitest run --config vitest.config.js tests/unit/social-feed-service.test.js
```

Single E2E spec / one browser (WebKit and Firefox need `pnpm exec playwright install-deps`; `E2E_BROWSERS` narrows the matrix, but CI must run all five):

```sh
pnpm exec nx run save-philly-festivals:e2e --args="e2e/smoke.spec.js"
cd apps/save-philly-festivals && ../../node_modules/.bin/playwright test --config playwright.config.js e2e/smoke.spec.js
E2E_BROWSERS=chromium pnpm run e2e
```

Note the vitest `include` is `tests/unit/**/*.test.js` relative to the app dir, so a root-relative path argument silently matches zero files rather than erroring usefully.

Database:

```sh
pnpm exec nx run save-philly-festivals:prisma-generate   # regenerate client into src/generated/prisma
pnpm exec nx run save-philly-festivals:prisma-validate
pnpm run migrate:test        # applies committed migrations to a blank local test DB
pnpm run db:seed && pnpm run db:verify-admin
```

N8N (`pnpm run n8n:init | validate | plan | deploy | health | logs | stop`). Deployment is gated: `CONFIRM_DEPLOY=n8n pnpm run n8n:deploy`. Never run `docker compose down --volumes`.

## Prisma layout — important

The schema lives at `apps/save-philly-festivals/prisma/schema.prisma`. Two configs point at it and they are kept deliberately equivalent:

- `apps/save-philly-festivals/prisma.config.ts` — what Nx targets use (`cwd: {projectRoot}`)
- `prisma.config.ts` at the repo root — resolves to the same schema, migrations, and env files, so bare `pnpm exec prisma <cmd>` works from the root

Historically the root config declared `schema: "prisma/schema.prisma"` against a root `prisma/` directory that had only a `seed.mjs`, so root-level Prisma commands failed with `Could not load schema … file or directory not found` while the identical command worked from the app directory. It also read a **different** `DATABASE_URL` from the root `.env`, pointing at a second Neon endpoint. Both are fixed: the root config forwards to the app, the stale root seed is gone, and there is one database. Don't reintroduce a root-local schema path.

`postinstall` and `.github/workflows/deploy.yml` still pass `--config apps/save-philly-festivals/prisma.config.ts` explicitly, which remains correct.

Prisma 7 specifics: generator is `prisma-client` (not `prisma-client-js`) emitting to `src/generated/prisma` (gitignored — generate after a fresh clone). Runtime uses the driver adapter `@prisma/adapter-pg` wired in `src/lib/db.js`; there is no `url` in the `datasource` block, so `DATABASE_URL` comes from `prisma.config.ts` for CLI and from the adapter at runtime. Production releases use `prisma migrate deploy`; `prisma db push` is not a release mechanism.

## Application architecture

Routes are thin; features own the logic. A `src/app/api/**/route.js` file typically just re-exports handlers:

```js
import { handleUserCreate, handleUserList } from "@/features/users/user-http";
export function GET(request) { return handleUserList(request); }
```

Each domain in `src/features/<domain>/` follows the same file-name layering, and this convention is the fastest way to find things:

- `*-schema.js` — Zod schemas plus body-size limits
- `*-http.js` — request parsing, content-type/size enforcement, status codes, `Cache-Control: private, no-store`
- `*-authorization.js` / `*-request-security.js` — role checks, origin enforcement, rate limiting
- `*-service.js` — business rules and state transitions
- `*-repository.js` — the only layer that touches `prisma`
- `*-e2e-fixture.js` — see below
- `*.jsx` — the feature's React components, colocated

Handlers resolve their collaborators through an async `dependencies()` indirection so tests and E2E can inject substitutes; keep new handlers on that pattern rather than importing `prisma` or `auth` directly into HTTP code.

**E2E fixtures are env-gated dependency swaps, not mocks in the test file.** `playwright.config.js` sets `DISCOVERY_E2E_FIXTURE=1`, `PRODUCER_E2E_FIXTURE=1`, and a generated `PRODUCER_E2E_SECRET`; the matching `*-e2e-fixture.js` module returns a fake repository/session when its flag is set, and `null` otherwise so production takes the real path. When adding a feature that needs E2E coverage, add its fixture alongside and gate it the same way.

Auth: `src/lib/auth.js` is Auth.js v5 with a credentials provider (bcrypt against `User.password_hash`), JWT sessions carrying `id` and `role`, sign-in page `/login`. It throws at import time if `AUTH_SECRET` is missing. Only `status === "active"` users can authenticate. Route groups split the surface: `(public)`, `(auth)`, `admin`, `producer`, `crm`.

Data model highlights (`prisma/schema.prisma`, ~60 models/enums): `Festival` is the hub, moving through `FestivalWorkflowState` (draft → pending_review → approved → published → …) with `FestivalTransition` and `FestivalRevision` audit trails. Other clusters: festival import batches (`FestivalImportBatch/Row/Issue`), social feed ingestion and moderation, organizer mailing consent plus an outbox, schedules and schedule-email delivery, and user account transitions.

**Public visibility is gated on `workflow_state`, and that gate catches people out.** `src/features/editorial-workflow/publication-policy.js` is the single source of truth: discovery/search and the calendar use `publishedDiscoveryWhere` (`workflow_state: "published"` only); detail pages additionally allow a `canceled` festival that was once published, as a tombstone. Because `festival-import-repository.js` creates every imported row as `status: "draft", workflow_state: "draft"`, **a completed CSV import is invisible on the public site until each festival is transitioned through to `published`.** "The import finished but search returns nothing" is expected behavior, not a bug in search — `src/features/festivals/public-discovery.js` queries the database directly and matches on `name`, `description`, `location`, `city`, and category name.

The import path also populates a deliberately narrow set of columns. The CSV contract is exactly 11 headers (`festival-import-csv.js`, `SOURCE_HEADERS`, enforced in order and asserted by `tests/unit/festival-import-csv.test.js`), with a SHA-256 checksum pin on the confirmed source file in `festival-import-profile.js`. Imported festivals therefore have no `description`, no `city`, and no imagery — which narrows what text search can match on them.

## Constraints worth knowing before you change things

- **`tests/unit/security-contract.test.js` reads source files as text** and asserts on them: `User.role` must default to `"public"` in the schema, the baseline migration must keep its historical `'admin'` default, and `prisma/seed.js` must require explicit `LOCAL_ADMIN_*` / `LOCAL_PRODUCER_*` credentials with no fallback passwords. Editing the schema, that migration, or the seed will break this test if you drift from the contract.
- `tests/unit/ui-components-contract.test.js` similarly requires admin/producer feature components to import `Button`/`Badge`/`Card`/`Dialog` from `@/components/ui/*` rather than hand-rolling them. `src/components/ui/` is shadcn-style primitives; `src/components/shared/` is app-specific.
- `src/lib/database-safety.js` refuses migration tests against any non-loopback host or a database whose name doesn't match `test`/`ci`. Don't loosen it to make a command run.
- Coverage in `vitest.config.js` uses an explicit `include` allowlist of files, not the whole tree — adding a module doesn't add it to coverage unless you list it.
- `next.config.mjs` sets a strict CSP (`object-src 'none'`, `frame-ancestors 'none'`, no external script/style origins) plus HSTS outside development. Third-party embeds will be blocked by design.
- `docs/Festivals_Postgres_Export.csv` and `*.festival-source.csv` contain organizer contact details, are gitignored, and belong in restricted storage only. Festival import reports are likewise gitignored.
- `apps/n8n/DiasporaDNA.json` is intentionally inactive and creates Gmail drafts only. Activation is always a separate, operator-approved action — a green CI run does not authorize deployment or activation.
- Environment: the app reads `apps/save-philly-festivals/.env.local` (then `.env`). `pnpm run auth:secret` generates `AUTH_SECRET`.
